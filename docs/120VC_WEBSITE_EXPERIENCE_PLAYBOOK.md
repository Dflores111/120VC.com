# 120VC Website Experience Playbook

Status: reusable teaching standard, compiled from the 120VC website design, copy, interaction, SEO, proof, and QA work through September 9, 2026.

This document teaches another AI or human collaborator how to continue the 120VC website without turning it into a generic consulting site, a keyword brochure, an interface demo, or a long document disguised as a webpage.

It separates three kinds of knowledge:

- **Settled standard:** a principle that repeatedly improved comprehension, trust, accessibility, or maintainability.
- **Current implementation:** a pattern that works in the present site and should be preserved unless a clearer buyer need justifies changing it.
- **Unresolved gate:** a business, proof, search, integration, or validation question that must not be invented away.

## 1. North star

The website should help an enterprise buyer:

1. recognize the execution problem they are experiencing;
2. understand what 120VC changes in the work;
3. see how the system works without learning internal jargon first;
4. evaluate fit and credibility with relevant evidence; and
5. confidently take the next appropriate step.

The experience should feel like a guided executive conversation: one question, one argument, one focal state, and one clear next action at a time.

The target feeling is confident, human, direct, intelligent, bold, editorial, useful, operational, enterprise credible, and alive without chaos.

## 2. The two planning contracts

### Page contract

Define every page through:

`Visitor → Question → Evidence → Next action`

Before choosing a layout, answer:

- Who is visiting?
- What do they already understand?
- What are they trying to determine?
- What single buyer question should this page answer?
- What evidence will help them decide?
- What is the most logical next action?
- What belongs on another page?

The page must also make four things immediately clear:

- Where am I?
- What is this telling me?
- What should I notice now?
- What should I do next?

### Interaction contract

Define every interactive element through:

`Intent → Signal → Trigger → Feedback → Outcome`

- **Intent:** the useful task or understanding it supports.
- **Signal:** how the visitor knows it is interactive.
- **Trigger:** click, tap, keyboard, hover, or native scroll.
- **Feedback:** what visibly changes immediately.
- **Outcome:** what the visitor gains or where they arrive.

Hover, focus, pressed state, pointer cursor, arrows, lift, scale, borders, and underlines are promises. Never apply them to a static object unless they lead to a real, predictable result.

## 3. Buyer journey and information hierarchy

Use `Recognize → Understand → Believe → Evaluate → Act` as a decision vocabulary, not a template every page must reproduce.

Typical page jobs:

| Page | Primary buyer question | Natural progression |
| --- | --- | --- |
| Homepage | Is this relevant, credible, and worth exploring? | Orient → Recognize → Believe → Route → Act |
| What We Solve | Is this the condition we are experiencing? | Recognize → Understand the cost → See what must change → Choose a next path |
| How We Help | What can 120VC do in our situation? | Identify application → Understand the work → Evaluate fit → Consult |
| How It Works | What is the mechanism and how is it installed? | Understand system → See sequence → See leader behavior → Evaluate |
| Results | Has this worked in relevant conditions? | See before/after → Inspect evidence → Understand attribution → Consult |
| Resources | Can I learn or use something before buying? | Choose intent → Use or read → Continue |
| Consultation | Is this a safe and useful next step? | Reduce risk → Set expectations → Share context → Confirm |
| About | Who are these people and why trust them? | Human evidence → Point of view → Credentials → Continue |

One section gets one dominant job, message, focal point, and primary action. If it tries to diagnose the problem, explain the system, show proof, sell three services, promote tools, and collect a lead, split it or move secondary information elsewhere.

### Current homepage baseline

The settled commercial sequence is:

`Attention → Trust → Recognition → Desire → Commercial clarity → Proof → Mechanism → Action`

A practical component map is:

1. human or video hero with the primary promise and consultation action;
2. approved client-logo rail for authority;
3. problem rail for self-recognition;
4. one bounded kinetic outcome statement for memory;
5. three clear How We Help application families;
6. one-case-at-a-time proof;
7. `Diagnose → Install → Operate → Own` mechanism; and
8. a still, direct final consultation action.

This is a buyer-journey baseline, not a frozen page template. Supporting pages should have their own job and composition rather than imitate every homepage interaction.

## 4. Messaging and copy

### Lead with the buyer, not the category

Use this order:

1. recognizable buyer problem or desired outcome;
2. plain-language explanation of what 120VC changes or installs;
3. concrete operational detail;
4. proof or credible evidence near the claim;
5. proprietary category or system language after the buyer has context;
6. one relevant action.

The current positioning hierarchy to verify against approved sources is:

- **Execution Leadership:** category;
- **Execution Leadership System:** mechanism or intellectual property;
- **Three Pillars and 120 Standard:** operating standard;
- **ELPA:** primary installation path;
- **The 120:** movement, identity, and standard.

Do not force a new visitor to understand this hierarchy before they recognize their own problem.

### Headlines are arguments, not labels

Navigation labels orient. Headlines persuade and explain.

Weak: `What We Solve`, `How We Help`, `How It Works`, `The five problems we solve`.

Stronger headlines name an observable condition, desired outcome, or meaningful change, such as priorities competing, decisions reopening, ownership staying unclear, transformations losing momentum, or portfolios consuming capacity without measurable return.

A page title and its H1 should not merely echo one another. The navigation label says where the visitor is; the H1 answers why the page matters.

### Copy rules

- Prefer a strong headline, one useful supporting sentence, and a component that carries the rest.
- Make every sentence orient, explain, persuade, reassure, substantiate, or help someone act.
- Use concrete nouns and verbs: priorities, decisions, ownership, capacity, transformation, portfolio, commitments, operating rhythm, measurable outcomes.
- Avoid abstract leadership-brand language, jargon-first writing, motivational coaching clichés, and generic consulting promises.
- Avoid repeated stacks of eyebrow, headline, subhead, label, description, and a second description.
- Avoid repeating the same phrase or complete list on every page. Repetition is not clarity.
- Use small text only for real orientation or function, such as `1 / 5`, `Back`, `Next`, `Diagnose`, `Install`, `Operate`, and `Own`.
- Do not shrink a headline before fixing its container, width, wrapping, or spacing.

### Current useful message direction

These lines show the approved direction, not a requirement to repeat them everywhere:

- `Priorities compete. Decisions reopen. Execution stalls.`
- `Clear priorities. Decisions that hold. Measurable results.`
- `Prioritize the work. Make the decision. Protect capacity.`
- `Align leaders. Make change stick. Focus the portfolio.`

## 5. SEO without sacrificing clarity

Search terms identify a page's subject. They do not dictate the site's voice.

### Rules

- Assign one primary search intent and topic owner to each indexable page.
- Put the primary topic naturally in the title, H1 or near-H1 context, description, body copy, metadata, and internal links where useful.
- Qualify broad terms with the buyer, problem, use case, or enterprise outcome.
- Use high-volume terms only when they match the page's buyer intent.
- Prefer topical ownership across the site over repeating `strategy execution` in every section.
- Keep important indexable content server-rendered; interaction may enhance it but should not be the only way it exists.
- Use canonical URLs deliberately. Aliases may return a shared experience, but should use the parent canonical and normally `noindex, follow` until evidence supports an independent page.
- Never delete or permanently redirect a route based only on design preference. Review traffic, backlinks, rankings, campaigns, collateral, and internal links first.

Search volume is not the same as ideal-client fit. The supplied keyword workbook was useful for architecture but was not treated as final market truth. Validate priorities with current first-party Search Console data, qualified conversions, and buyer language before making irreversible SEO changes.

## 6. Attention and visual hierarchy

Attention is a budget. In each viewport there should be one obvious first focal point.

Use scale, contrast, orange, uppercase, motion, and placement sparingly. When several elements compete, remove or de-emphasize before adding another visual effect.

### Local attention order

| Context | Intended reading order |
| --- | --- |
| Hero | H1 → human visual → description → primary CTA → secondary action |
| Problem rail | active card → neighboring cards → progress/controls → heading |
| Diagnostic | active stage title → central statement/evidence → stage control |
| Solutions | selected application → alternatives → supporting explanation |
| Proof | result/transformation → case title → before/change/after → context → CTA |
| Final CTA | headline → action → reassurance |

### Color and surface rhythm

Use semantic surface changes to mark chapters and prevent adjacent regions from merging. A dark section should not disappear into a footer of the same dark value without a clear boundary or intervening surface. Alternate warm light, sage, terracotta, and ink surfaces according to meaning and reading rhythm—not decoration.

Orange primarily communicates action, selection, direction, active state, or a rare brand accent. If everything is orange, nothing is selected.

### Typography

- Display type carries one decisive statement, not paragraphs.
- Body type should be comfortably readable with deliberate line length.
- Uppercase is an accent for status or orientation, not the default hierarchy.
- Balanced wrapping and container width come before reducing font size.
- Mobile should preserve the hierarchy, not merely shrink desktop geometry.

### Human imagery and diagrams

Use human photography to communicate pressure, collaboration, leadership dynamics, decision-making, relief, and agency. Use diagrams and icons to explain sequence, causality, prioritization, system relationships, ownership, and before/after change.

Stock photography may illustrate a situation. It must never imply customer proof.

## 7. Choose components by the information relationship

| Information relationship | Preferred component | What it should make easier |
| --- | --- | --- |
| One primary promise | Human/video or static hero | Understand the big idea |
| Credibility at a glance | Approved logo rail | Recognize legitimate relationships |
| Parallel buyer conditions | Manual card rail | Find the situation that feels familiar |
| One condition through several lenses | Fixed-stage diagnostic | Follow a single argument in order |
| Parallel applications or offers | Editorial cards/disclosures | Compare choices |
| Ordered installation | Stepper or timeline | Understand sequence |
| Connected operating system | Progressive system story or diagram | See relationships and causality |
| Separate case studies | Manual carousel | Review independent examples |
| Transformation inside a case | Before → 120VC Changed → After | Understand intervention and result |
| Optional detail | Accordion | Expand only when needed |
| Alternate views of one subject | Tabs | Switch lenses without implying sequence |
| Staged commitment | Progressive form | Start with low friction, add context later |
| Simple linear explanation | Semantic text and layout | Read without unnecessary interaction |

Do not use a stepper for parallel problems, a carousel for a mandatory sequence, a system diagram for separate offers, or a flip card to hide essential proof.

## 8. Settled component and interaction patterns

### Direct global navigation

Use a short buyer-facing header, not a sitemap. Keep core paths visible, show current location, include a clear consultation action, and keep all configured pages reachable through appropriate primary, contextual, footer, resource, legal, or CTA links.

The mobile menu must be a real dialog: predictable open/close state, focus containment, Escape dismissal, focus return, background isolation, and native links. Body scroll may be locked only while that menu is open.

### Compact footer

The footer is a closing orientation and trust surface, not a duplicate of the entire sitemap. Group only useful routes, legal links, and the brand statement. Give it visible separation from the section above.

### Finite hero outcome rotation

Rotating text can make the promise memorable when it resolves a single sentence into a small set of specific outcomes. It should:

- rotate through a finite sequence;
- stop on a deliberate final state;
- pause when the page is hidden;
- expose a stable equivalent to assistive technology; and
- show a stable version under reduced motion.

Do not auto-change essential meaning indefinitely.

### Credibility rail

Use client logos only when the relationship and public permission are approved. Continuous movement needs a pause mechanism, no hidden meaning, and a static reduced-motion layout.

### Horizontal problem rail with edge fades

For parallel problems:

- show progress such as `1 / 5`;
- provide previous/next controls and touch swipe;
- show part of the next card where space permits;
- apply a subtle left or right fade only when more content remains in that direction;
- remove the fade at the true start or end;
- keep the fade non-interactive and pointer-transparent;
- make the selected card visually distinct and scroll it into view; and
- provide an explicit selection action such as `View details`.

Hover or focus may preview secondary information, but Escape should dismiss it and no essential content may be hover-only.

### Selected-problem diagnostic

After selection, preserve one coherent argument:

`What you may be seeing → Why it matters → What leaders must change`

These are three lenses on one condition, not unrelated tabs. Use a connector between the selected card and diagnostic when it improves continuity. Persist selection in the URL and browser history so refresh, back, forward, and deep links are meaningful.

### Fixed-stage scroll story

For a dense sequence that should not become a long document, use a sticky visual stage while native page scroll advances discrete panels in the same footprint.

Requirements:

- normal passive page scrolling; no wheel interception or scroll trap;
- one dominant panel visible at a time;
- explicit numbered controls as an alternative to scrolling;
- short, finite progress with a visible stopping point;
- inactive panels removed from interaction and the accessibility tree;
- a compact stage height that fits common laptop viewports;
- content vertically balanced without excessive blank space;
- no-JavaScript fallback that returns panels to normal document flow; and
- reduced-motion behavior that removes smooth travel and exposes a stable, understandable state.

This pattern is appropriate for the three-stage diagnostic, the six-part execution system, and Before/Changed/After proof. It is not a license to turn every section into a scrollytelling sequence.

### One-time scroll reveal

Use entrance reveals to establish reading order, not to conceal the page. Reveal the scene once when it enters the viewport, then leave it readable. Mark only the headline, up to a few supporting elements, the primary visual, and short sequence items. The initial/non-JavaScript state must remain visible; reduced motion should remove the transition.

### Installation stepper

Use a stepper for `Diagnose → Install → Operate → Own` because the relationship is ordered. Advance manually or through bounded scroll only when the sequence remains controllable, readable, and keyboard accessible. On mobile, convert a horizontal stepper into a vertical reading path.

### Proof carousel

Show one case at a time. Within the selected case, tell one legible story:

`Before → 120VC Changed → After`

Use one dominant result, a clear intervention, concise context, an approved quote when available, and an honest deeper action. Case navigation is manual; it must not auto-advance while the buyer is reading.

If motion helps, reveal Before, move one connection through the intervention, resolve After, count the main result once, then become still.

### Resource organization

Organize resources by visitor intent, such as `Use the system` and `Understand the system`, rather than by internal CMS type. Tabs are appropriate for alternate categories; accordions are appropriate for optional detail. Never make an unfinished resource look functional.

### Progressive consultation form

Start with low-friction identity and context, then ask about the execution condition and timing. Explain what the consultation is, who should participate, what to bring, and what happens after submission.

A mail link, form-opening interaction, pending request, or button click is not a successful submission. Show success only when the destination system confirms receipt. Preserve source/route/UTM context without collecting unnecessary sensitive data.

## 9. Motion and scroll choreography

Use more motion only when it results in fewer moving ideas.

Motion may:

- explain a change;
- direct attention;
- make a sequence legible;
- create memory around one message;
- demonstrate cause and effect; or
- support browsing.

Avoid repeated generic fade-ups, random parallax, floating cards, decorative particles, multiple marquees in one viewport, hover-only flips, auto-advancing proof, and animation that never settles.

One section generally owns one motion language. Separate active passages with quiet ones. Stillness is part of the choreography; a static final CTA often feels stronger after an active page.

Prefer transform and opacity animation to layout-changing properties. Bound the duration and travel. Respect page visibility. Every animated state needs a final state, and every persistent motion needs a pause path.

## 10. Progressive disclosure and density

Show the minimum needed for the current decision, not the minimum needed to make the layout look clean.

Keep the essential meaning, critical risk, primary proof, pricing when relevant, and only CTA visible. Progressively disclose supporting symptoms, delivery detail, practices, methodology, secondary proof, and FAQs.

Use these density rules:

- one dominant state per viewport;
- no more than a few readable lines in a focal panel;
- one decisive heading instead of many nested labels;
- fixed stages should be compact enough to fit common laptop heights;
- reduce padding and unused stage height before shrinking type;
- if a component needs a paragraph explaining how to use it, make the component more familiar; and
- if interaction adds no clarity, use a static semantic layout.

## 11. Accessibility and responsive behavior

Target WCAG 2.2 AA and test actual behavior.

- Preserve native links and buttons.
- Support mouse, keyboard, touch, and screen readers.
- Make focus visible and follow a logical order.
- Support Enter/Space activation where expected.
- Use Escape to dismiss temporary previews, dialogs, and menus.
- Give touch targets comfortable size and separation.
- Announce meaningful state changes without announcing decorative motion.
- Mark inactive overlaid panels `aria-hidden` and `inert` so only the current state is operable.
- Never make hover the only path to meaning.
- Preserve content and orientation under reduced motion.
- Preserve a readable no-JavaScript fallback for scroll narratives.

Responsive design should preserve the mental model:

| Component | Desktop | Mobile |
| --- | --- | --- |
| Problem rail | several cards plus a partial next card | about one card plus a continuation cue |
| Stepper | horizontal sequence | vertical sequence |
| Before/Changed/After | staged or column transformation | staged or stacked transformation |
| Solution families | parallel cards | stacked disclosures |
| Fixed-stage story | compact sticky canvas | shorter canvas or normal-flow fallback when needed |

## 12. Proof and claim governance

Proof is a conversion system and a publication gate.

Verify before publication:

- client and logo relationship;
- permission to use name, logo, quote, and result;
- baseline and measurement period;
- measurement method and attribution;
- context needed to interpret the metric;
- approval date and artifact owner.

Never fabricate or imply evidence. Mark design-only evidence `PLACEHOLDER — NOT APPROVED FOR PUBLICATION`; mark invented quotes `PLACEHOLDER TESTIMONIAL — NOT APPROVED FOR PUBLICATION`; prevent both from public builds.

Do not publish historical `98%`, `227%`, industry-comparison, or other claims unless the current approval record substantiates the exact wording, denominator, period, method, and permission.

Use one approval record to govern the same claim everywhere it appears: homepage, Results, navigation teasers, structured data, metadata, and case-study routes.

## 13. Conversion and measurement

Support different readiness levels while maintaining one clear primary action:

| Readiness | Appropriate next step |
| --- | --- |
| High intent | Book a Leadership System Consultation |
| Medium intent | Read a case, compare help, or see how it works |
| Early intent | Use a tool, read a resource, or explore a diagnostic |

Every CTA must say what happens next. Avoid generic `Learn more` when a more specific label is available.

Track useful outcomes rather than motion for its own sake:

- problem selected;
- diagnostic completed or advanced;
- solution explored;
- case viewed;
- resource opened;
- consultation started;
- consultation successfully received.

Do not record success when only the client-side animation or click occurred. Keep analytics privacy-safe and distinguish engagement from qualified business outcomes.

## 14. Navigation, routes, and publication

Primary navigation should represent the buyer's core decisions, not mirror the complete route inventory.

At the same time, `all pages included` means every configured route must remain intentionally reachable through header, contextual links, CTAs, Resources, footer, or legal navigation. Verify:

- header and mobile menu;
- footer and legal links;
- buttons and contextual CTAs;
- resource destinations;
- aliases and canonical behavior;
- sitemap and metadata;
- representative deep routes; and
- the published surface, not only localhost.

Preserve the existing site project, public URL, visual identity, and working capabilities unless replacement is explicitly requested.

Publication is not complete when a build passes or a deployment is pending. It is complete only after the exact intended source is deployed successfully and the live public URL is verified.

## 15. Maintainable implementation

- Keep page content, route data, proof records, and business facts separate from presentation.
- Reuse shared header, footer, button, surface, motion, and stage primitives.
- Centralize route inventory and derive navigation and sitemap behavior from reliable data.
- Store selected state in the URL when it needs to survive refresh, deep linking, back, and forward.
- Use feature or review modes for nonproduction proof rather than scattering conditional copy.
- Add dependencies only when their benefit exceeds the accessibility, performance, and maintenance cost.
- Treat external component prompts as capability specimens. Adapt them to the actual framework, semantics, content, and interaction contract.

## 16. What we intentionally rejected

- Headlines that only state the page topic.
- Jargon before the buyer recognizes the problem.
- Keyword repetition that makes copy sound written for a crawler.
- Equal card grids and equal CTAs everywhere.
- Multiple focus points, labels, metrics, and animations in one viewport.
- Long scroll documents created by stacking every state vertically.
- Scroll hijacking, wheel interception, or hidden exit paths.
- Persistent auto-rotating essential copy.
- Autoplay case studies or proof.
- Decorative hover, lift, arrows, underlines, and cursor changes with no action.
- Hover-only information.
- Edge fades that remain visible when there is no more horizontal content.
- A dark final section visually merging into the dark footer.
- Giant fixed stages with mostly empty space.
- Shrinking typography to repair a container problem.
- Abstract dashboards or diagrams that make the buyer assemble the story.
- Multiple metrics fighting for attention.
- Stock imagery presented as evidence.
- Unapproved logos, testimonials, metrics, or success claims.
- Resource cards that promise tools or actions that do not exist.
- Forms that celebrate a click instead of confirmed receipt.
- Treating automated string checks, hashes, or screenshots as full usability validation.

## 17. Preserve-first improvement workflow

Use:

`Understand → Structure → Gather evidence → Design → Build → Test → Refine → Measure`

### Step 1: Understand

- Read the brief, current page, route data, approved copy, proof records, and search inputs.
- Define the visitor, question, evidence, and next action.
- Write a short Preserve List before proposing changes.

### Step 2: Structure

- Map the page's decision journey.
- Give each section one job.
- Remove duplicated arguments and route detail to the right page.

### Step 3: Gather evidence

- Classify every claim as verified, approved, placeholder, unresolved, or missing.
- Separate current first-party evidence from historical decks, demo data, and design copy.

### Step 4: Design

- Choose components by information relationship.
- Define the attention order, interaction contract, responsive transformation, and motion purpose.
- Specify reduced-motion and no-JavaScript behavior before implementation.

### Step 5: Build

- Preserve shared architecture and unrelated user work.
- Implement the narrow approved change.
- Keep essential meaning server-rendered and semantically structured.

### Step 6: Test

- Run syntax, type, lint, unit, route, and build checks appropriate to the project.
- Inspect the rendered experience near 320, 390, 768, 1024, and 1440 pixels.
- Exercise pointer, touch-equivalent, keyboard, focus, Escape, reduced motion, overflow, forms, links, and failure paths.

### Step 7: Refine

- Ask what is seen first, whether the argument is clear, whether interaction is obvious, and whether anything competes or feels tacked on.
- Reduce empty height, duplicate copy, and competing accents before adding visual novelty.

### Step 8: Measure

- Verify live routes and conversion behavior.
- Use representative buyers and first-party analytics to learn whether the page improves comprehension, progression, and qualified action.
- Do not claim conversion improvement without measurement.

## 18. Evidence ladder for truthful status

Never collapse these levels into one:

1. **Specified:** intended behavior is documented.
2. **Built:** source contains the implementation.
3. **Test-passing:** automated checks pass.
4. **Rendered:** the relevant states and widths were visually inspected.
5. **Live:** the exact version was successfully published and checked at the public URL.
6. **Approved:** business owners approved claims, proof, and usage rights.
7. **Effective:** representative-user or business measurement shows the intended outcome.

A build hash proves artifact identity, not buyer comprehension. A screenshot proves one state, not full behavior. Reduced-motion screenshots cannot verify normal motion. Localhost does not prove the published site.

## 19. Acceptance checklist

### Comprehension

- [ ] The H1 communicates a specific buyer problem, outcome, or change.
- [ ] The page answers one primary buyer question.
- [ ] Proprietary language is explained after recognizable context.
- [ ] Each section has one job and one focal point.
- [ ] Secondary information is disclosed or routed without hiding essentials.

### Components and interaction

- [ ] Every component matches the relationship it explains.
- [ ] Every apparent control has a real outcome.
- [ ] Scroll-led sections use native scrolling and have explicit alternatives.
- [ ] Sliders show directional continuation only when more content exists.
- [ ] One active state is visible and operable at a time.
- [ ] Motion settles, pauses when needed, and has a reduced-motion equivalent.

### Credibility and conversion

- [ ] Evidence appears near the claim it supports.
- [ ] No unapproved proof or placeholder reaches production.
- [ ] The primary CTA matches buyer readiness and states what happens next.
- [ ] Form success means confirmed receipt.
- [ ] Resource and service promises match actual functionality.

### SEO and navigation

- [ ] Each indexable page owns a distinct buyer/search topic.
- [ ] Metadata, H1, copy, internal links, canonical, and index state agree.
- [ ] Every configured route and destination resolves.
- [ ] Header, mobile menu, footer, resources, CTAs, and legal navigation work.
- [ ] The live public surface was checked after successful deployment.

### Quality and accessibility

- [ ] Real phone, tablet, laptop, and wide layouts were inspected.
- [ ] Keyboard order, focus, Escape, touch, and screen-reader states are coherent.
- [ ] No clipping, overflow, collision, or unusably empty stage remains.
- [ ] Reduced-motion and no-JavaScript fallbacks preserve meaning.
- [ ] The page feels composed, not assembled from unrelated components.

## 20. Unresolved gates

The following are not design problems an AI may solve by inventing completion:

- current first-party search volume and qualified-query evidence;
- approved client logos and the exact relationship each represents;
- approved case studies, quotes, metrics, baselines, attribution, and usage rights;
- substantiation for historical performance claims;
- confirmed CRM or form-submission receipt behavior;
- image licensing and source rights where not already documented;
- real-user comprehension and conversion measurement;
- current Core Web Vitals and production performance evidence.

## 21. Compact instruction for another AI

Use this when handing the website to another AI:

> Improve the 120VC website as a guided enterprise-buyer conversation. Start every page with `visitor → question → evidence → next action`; lead with recognizable execution problems and concrete operational outcomes before proprietary language; give every section one job and every interaction an `Intent → Signal → Trigger → Feedback → Outcome` contract. Select components by the information relationship. Use native, bounded scroll storytelling only when it lets one state replace another in a compact fixed stage; never hijack scrolling, hide essential meaning, or create a long document. Preserve keyboard, touch, reduced-motion, no-JavaScript, URL-state, route, navigation, and live-deployment behavior. Treat SEO as page-topic ownership, not keyword repetition. Never invent proof, claims, destinations, or submission success. Distinguish specified, built, test-passing, rendered, live, approved, and effective states. Inspect the current implementation and write a Preserve List before changing it.
